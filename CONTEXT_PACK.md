# CONTEXT_PACK.md

## Проблема и чья это работа

Brand Analytics нужно автоматически извлекать из узбекоязычных текстов сущности трех типов: ORG, NAME и GEO, чтобы использовать их в аналитике по информационному полю Узбекистана.

Основной пользователь результата не работает с NER напрямую. Это внутренний компонент конвейера Brand Analytics, а конечные пользователи — PR-специалисты, маркетологи и аналитики, которые получают агрегированную аналитику по организациям, людям и географии.

Проблема возникает до этапа построения отчетов: если сущности в узбекском тексте не распознаны или распознаны неверно, часть упоминаний теряется, а часть аналитики загрязняется ложными сущностями.

## Как это работает сейчас и что это стоит

Для русского и английского языков NER уже используется в продукте. Для узбекского полноценного промышленного сервиса пока нет.

Из-за этого аналитика по рынку Узбекистана получается менее полной. Клиентам приходится тратить больше времени на ручной поиск и проверку упоминаний, а Brand Analytics сложнее полноценно развивать продукт на этом сегменте.

Точная денежная стоимость проблемы, стоимость ручной обработки и объем потерянной выручки в материалах кейса не указаны.

Известные production-ограничения:

- поток узбекских сообщений около 30 RPS;
- обработка идет батчами;
- желательная latency до 5 секунд;
- основное железо — NVIDIA A100;
- при одинаковом качестве предпочтительнее более компактная модель;
- для production желательны модели до 1 млрд параметров;
- human-in-the-loop на inference нет.

## Обязательные требования кейса и наши предположения

| Обязательные требования кейса | Наши предположения и рабочие решения |
| --- | --- |
| Извлекать ORG, NAME и GEO | Основной backbone — XLM-R Large |
| Возвращать точные start/end | BIOES + CRF + отдельные START/END heads |
| Работать с латиницей, кириллицей и mixed-текстами | Multilingual encoder + script-aware augmentation |
| Поддерживать длинные тексты | Sliding window с overlap и merge |
| Воспроизводимое и возобновляемое обучение | YAML-конфиги, checkpoints, resume_from_checkpoint |
| Docker и HTTP API | FastAPI + NVIDIA Triton |
| Метрика — exact-span Micro F1 | HPO оптимизируется по официальному evaluator |
| Production на A100 | ONNX Runtime FP16 как базовый serving-вариант |
| При равном качестве лучше меньшая модель | Не использовать LLM как основной inference-путь без явного выигрыша по качеству |
| Бонус: нормализация и дедупликация | Не входит в основную реализацию на текущем этапе |

Предположения из правой колонки еще требуют проверки экспериментами. Итоговый прирост CRF, gazetteer, boundary heads, DAPT и других компонентов пока не подтвержден финальными метриками.

### Повторяемость сущностей

Около 58% dev-упоминаний уже встречались в train в точном написании.

После casefold и безопасной нормализации вариантов апострофов — около 60%.

По классам:

- GEO — около 73.6%;
- ORG — около 62.2%;
- NAME — около 42.9%.

Этот результат стал основанием для проверки gazetteer-подхода.

### Границы сущностей

По правилам разметки присоединенные морфологические окончания в ряде случаев входят в gold span.

Примеры:

- Kanadaning
- Nigeriyadagi
- AQShga
- BMW'da
- Тошкент вилоятининг

Поэтому нельзя автоматически отрезать падежные окончания или нормализовать сущность до словарной формы в основной задаче.

## Аналоги и чем хотим отличаться

### 1. Baseline организаторов

Использует multilingual DistilBERT и обычный token classification.

Наше отличие:

- более сильный multilingual backbone;
- BIOES вместо простого BIO;
- CRF;
- gazetteer;
- boundary heads;
- HPO;
- production serving через Triton.

Фактический выигрыш относительно baseline еще не измерен.

### 2. XLM-R token classification

Классический сильный multilingual NER baseline.

Наше отличие:

- gazetteer как дополнительный лексический prior;
- отдельное моделирование границ;
- out-of-fold словарь для защиты от leakage;
- отдельная работа с длинными текстами и exact offsets.

### 3. GLiNER / span-based NER

Сильный класс решений, который напрямую работает со span-кандидатами.

Наше отличие:

- основное решение остается ближе к стандартному production token-classification pipeline;
- проще экспортировать и обслуживать;
- лучше контролируется exact offset mapping.

GLiNER пока не сравнивался с нашим решением на предоставленном датасете.

### 4. LLM + LoRA

Можно дообучить небольшую multilingual LLM и просить ее извлекать сущности.

Наше отличие:

- меньше latency;
- проще exact-span alignment;
- один encoder forward вместо autoregressive generation;
- более естественный production fit под 30 RPS.

LLM-ветка пока не закрыта окончательно и может быть протестирована как дополнительный эксперимент.

### 5. Gazetteer-only / rule-based NER

Хорошо работает на известных сущностях, но плохо обобщается на unseen.

Наше отличие:

- gazetteer не принимает решение сам;
- словарный сигнал объединяется с контекстом XLM-R;
- модель сохраняет способность находить новые NAME, ORG и GEO.

## Рабочие гипотезы

1. XLM-R Large даст более сильный baseline, чем multilingual DistilBERT организаторов.

2. BIOES + CRF улучшит exact-span качество на multi-token сущностях.

3. Gazetteer даст заметный прирост прежде всего на GEO и ORG, где повторяемость между train и dev выше.

4. START/END heads уменьшат ошибки на границах сущностей.

5. Script-aware augmentation повысит устойчивость на Latin, Cyrillic и mixed-текстах.

6. DAPT на узбекских новостях и социальных текстах может улучшить качество на редких и доменных сущностях.

7. Рискованная гипотеза: сложная гибридная архитектура XLM-R + gazetteer + CRF + boundary heads даст достаточный прирост, чтобы оправдать дополнительную сложность по сравнению с более простым XLM-R baseline.

На текущем этапе эти гипотезы не считаются подтвержденными. Для каждой нужен отдельный ablation.

## Как используем ИИ в процессе

ИИ используется как вспомогательный инструмент, а не как источник финальных неподтвержденных результатов.

Используем для:

- поиска и сравнения исследовательских подходов;
- подготовки вариантов архитектуры;
- ревью технических решений;
- помощи с шаблонами кода и конфигураций;
- подготовки документации;
- систематизации EDA и error analysis;
- проверки альтернативных гипотез.

Результаты, метрики и выводы по качеству модели считаются подтвержденными только после запуска собственного кода на предоставленных данных и проверки официальным evaluator.
