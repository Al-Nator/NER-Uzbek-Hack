# Контракт инференс-сервиса

Итоговое решение должно запускаться в Docker и предоставлять два HTTP-эндпоинта:

- `GET /healthz` — лёгкая проверка доступности сервиса;
- `POST /api/v1/predict` — выделение сущностей в батче текстов.

Сервис должен слушать `0.0.0.0:8000` и принимать и возвращать JSON в кодировке
UTF-8. Авторизация не требуется.

## Проверка доступности

### `GET /healthz`

Эндпоинт не должен запускать инференс или выполнять другую тяжёлую операцию.
После загрузки модели и готовности обрабатывать запросы он должен возвращать:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{"status":"ok"}
```

Пока модель загружается, сервис может не принимать соединения или возвращать
`503 Service Unavailable`. Отдельный эндпоинт готовности не требуется.

## Предсказание

### `POST /api/v1/predict`

Тело запроса — непустой JSON-массив. Каждый элемент содержит уникальный в
пределах запроса идентификатор и текст:

```json
[
  {
    "hash": "example-001",
    "text": "Ali Toshkent shahrida ishlaydi."
  },
  {
    "hash": "example-002",
    "text": "Алишер Навоий ҳақида мақола."
  }
]
```

Успешный ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "data": [
    {
      "hash": "example-001",
      "entities": [
        {"label": "NAME", "start": 0, "end": 3},
        {"label": "GEO", "start": 4, "end": 12}
      ]
    },
    {
      "hash": "example-002",
      "entities": [
        {"label": "NAME", "start": 0, "end": 13}
      ]
    }
  ]
}
```

Требования к ответу:

- `data` содержит ровно один результат для каждого входного элемента, в том же
  порядке;
- `hash` без изменений копируется из соответствующего входного элемента;
- `entities` всегда является массивом, в том числе когда сущности не найдены;
- `label` принимает одно из значений `ORG`, `NAME`, `GEO`;
- `start` и `end` — целые символьные координаты в исходном `text`;
- используется полуинтервал `[start, end)`: `start` включается, `end` не
  включается;
- координаты считаются с нуля по символам Unicode, как индексы строки Python, а
  не по байтам;
- для каждой сущности должно выполняться `0 <= start < end <= len(text)`;
- одинаковая сущность не должна повторяться в ответе.

Порядок сущностей внутри `entities` не влияет на расчёт метрик. Дополнительные
поля в объектах ответа разрешены, но при оценке не используются. Для
некорректного запроса сервис должен возвращать код `4xx`, а не `200` с
частичным результатом.

## Docker-контракт

В корне передаваемого решения должен находиться `Dockerfile`. Организаторы
должны иметь возможность собрать образ командой:

```bash
docker build -t ner-uz-solution .
```

И запустить сервис командой:

```bash
docker run --rm -p 8000:8000 ner-uz-solution
```

Если решение требует NVIDIA GPU, команда запуска дополняется параметром
`--gpus all`. Это требование необходимо явно указать в документации команды.

После сборки образ должен запускаться без монтирования дополнительных файлов,
секретов и обязательных переменных окружения. Модель и все необходимые для
инференса ресурсы должны находиться внутри образа. Во время работы контейнер не
должен скачивать модель, обращаться к внешним API или требовать доступ в
интернет.

Время загрузки модели не ограничивается самим HTTP-контрактом. Проверяющий
скрипт ожидает успешного ответа `/healthz` перед отправкой запроса на
предсказание.

## Локальная проверка

После запуска контейнера проверить обязательные эндпоинты и формат ответа можно
командой:

```bash
python scripts/check_service.py --url http://localhost:8000
```

Проверка подтверждает совместимость формата, но не оценивает качество модели.

Для полного прогона сервиса на валидационной выборке и расчёта метрик:

```bash
python scripts/evaluate_service.py \
  --url http://localhost:8000 \
  --gold data/dev.jsonl
```
